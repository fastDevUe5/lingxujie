## 一、🔴 之前所有走法都错在哪

**我一共试过三种块头长度：28 字节、30 字节、12 字节 —— 全错。**

**正确的块头是 **8 字节**：**

```
+0  u32  block_type      (标记符，见第二节)
+4  u32  block_size      (载荷字节数，不含这 8 字节头)
+8  载荷开始
```

**验证方式：走完全部 40 个块，分类计数与文件头声明的计数**精确匹配**：**

```
w25260.mod  (25,951 字节, 声明 39 对象 / 1 材质 / 1 网格 / 38 骨骼)
  实际走到: MATERIAL×1, BONE×38, MESH×1  = 40 块
  ⚠️ 40 ≠ 39 —— 差 1，原因见第四节

jp03_dht00.mod  (5,203 字节, 声明 5 对象 / 1 材质 / 1 网格 / 4 骨骼)
  实际走到: MATERIAL×1, BONE×4, MESH×1   = 6 块
  ⚠️ 6 ≠ 5 —— 同样差 1
```

**两个文件都差 1，说明**「对象数」不含网格**：**
```
materials + bones = objects
jp03: 1 + 4 = 5  ✓
w25260: 1 + 38 = 39  ✓
```

## 二、块类型标记（本轮新确证）

**标记不是常量 —— 我之前要求它固定，这就是走不通的原因。**

| 标记（u32 LE） | 类型 | 证据 |
| --- | --- | --- |
| **`0x00F00000`** | **MATERIAL** | 两个文件的第一块都是它 |
| **`0xF5000000`** | **BONE** | 载荷第一个 int = 骨骼编号，倒序（4,3,2,1）|
| **`0xF4000000`** | **MESH** | 载荷最大，含单位向量数组 |

**⚠️ 上一版文档说「`0xF000`+size+20 零+名字」—— 那是**错的**，名字字段在载荷里，不在头里。**

## 四、骨架块（部分确认）

**每个骨骼块约 588–600 字节，载荷第一个 int 是**骨骼编号**。**

**jp03_dht00 实测（4 骨骼，倒序存储）：**
```
[1] @1480  size=588  word0=4   ← Bone04
[2] @2076  size=592  word0=3   ← Bone03
[3] @2676  size=592  word0=2   ← Bone02
[4] @3276  size=592  word0=1   ← Bone01
```

**⚠️ 倒序存储**意味着网格里的骨骼索引可能也是**从后往前**算的。
**这解释了为什么之前按正序找父骨骼会对不上。**

## 五、网格载荷：结构比预想复杂

**用「单位长度向量」这个数学特征扫描，发现**多个**单位向量数组，不是一组：**

**w25260（32 顶点，载荷 1,620 字节）：**
```
+0    = 14                 <- 一个计数
+24   = 14 个单位向量（首值 (0,0,1)）
+360  = 55 个单位向量（首值 (-0.29,0.11,-0.95)）
+1236 = 32 个单位向量      <- 与顶点数 32 匹配
```

**jp03_dht00（载荷 1,272 字节）：**
```
+1152 = 10 个单位向量
```

**结论：载荷里有**多组**向量（法线 / 切线 / 可能的骨骼方向），
而且**没有一组的数量与顶点数稳定对应**。**

**⚠️ 上一版文档说「+36 开始是法线」—— 也是**错的**，法线在载荷**靠后**位置。**

## 六、蒙皮权重：仍未找到（诚实）

**我做过的尝试：**

| 尝试 | 结果 |
| --- | --- |
| 按「每顶点 4 权重之和 = 255」扫描 u8 | ❌ 无匹配 |
| 按 u16 之和 = 65535 扫描 | ❌ 无匹配 |
| 按 f32 之和 = 1.0 扫描 | ❌ 无匹配 |
| 按块行走找载荷结构 | ✅ **容器格式搞清了**（本轮成果）|

**扫描没找到的原因可能是：**
1. **每顶点影响数不是 4**（头部 +12 字段在正确块里可能不是这个含义）
2. **权重不是归一化的**（原引擎可能存原始权重，运行时才归一化）
3. **权重和骨骼索引交错存**（不是先全索引再全权重）

## 十、批量扫描结果（第 13 轮，2026-11-26）

### 10.1 先按骨骼数过滤 —— 这一步之前漏了

**全库 5,305 个 `.mod`，其中：**

| 类别 | 数量 |
| --- | --- |
| `bones = 0`（静态道具/特效）| **3,412** |
| **`bones > 0`（有骨架）** | **1,893** |
| 其中 `bones > 60`（角色体型）| **1,385** |

**第一批扫描扫的是字母序前 40 个 —— 几乎全是 `bones=0` 的道具。
那批数据说明的是**布景**的结构，不是角色的。**

### 10.2 角色模型的单位向量数组模式

**按骨骼数分桶，每组取 8 个样本：**

| 桶 | 模型数 | 典型单位向量数组 |
| --- | --- | --- |
| `<16` 骨骼 | 24 | `40:2, 124:2`（**只有头部两个小数组**）|
| `16-59` | 121 | 同上，偶尔后面有长串 |
| `60+` | 778 | 同上 |

**`40:2, 124:2` 的含义：载荷 +40 和 +124 各有 **2 个**连续单位向量。**

**这两个是**头部固定字段**（可能是默认朝向），不是几何。**

### 10.3 🔴 两个否定结论（重要）

**我验证了两种浮点格式，都不是：**

| 假设 | 验证方法 | 结果 |
| --- | --- | --- |
| 法线是 **f32** 单位向量 | 扫 12 字节三元组，长度≈1.0 | **大多数角色找不到** |
| 法线是 **f16**（半精度）单位向量 | 扫 6 字节三元组，长度≈1.0 | **全部找不到（0 个）** |

**而少数模型确实有 f32 单位向量：**
```
19240.mod    (96 骨骼)  载荷 14,676  找到 348 个（@10500）
costume_wing_14.mod     载荷 178,580 找到一串 @53540 起，间距 44 字节
```

**所以：f32 法线只在**部分**模型里存在，多数角色没有。**

### 10.4 由此推出的新假设

> **法线很可能是**字节量化**的：每个法线 3 个 u8，值域 [-1,1] 映射到 [0,255] 或 [-127,127]，
> 加载时归一化。**

**依据：**
1. 墨香是 2000 年代引擎，字节量化法线在当时是标准做法（省 4 倍内存）
2. 用 f32 和 f16 都扫不到，说明不是浮点
3. 载荷大小与「位置 f32 + 法线 u8」的比例吻合

**验证方法（下一轮第一件事）：**
```
对每个角色载荷，假设:
  位置 = f32 x 3 x vertexcount
  法线 = u8  x 3 x vertexcount
遍历 vertexcount 的可能值，检查「法线段」每个三元组字节归一化后的长度是否 ≈ 1.0
```
