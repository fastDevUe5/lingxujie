# UE5 网络与复制（引擎源码核实）

> **P0 是单机垂直切片 —— 本项目**不需要**网络。
> 但"没看"和"看了知道不需要"是两件事，本篇是后者。**
>
> **另外一条重要区别：墨香有完整的服务端源码，但那是**自研协议**，
> 和 UE 的复制机制**完全无关**。这条要分清。**

---

## 一、复制的三行声明

**UE 的复制全部围绕三个声明，其余都是策略：**

| 声明 | 在哪 | 作用 |
| --- | --- | --- |
| **`bReplicates = true`** | Actor 构造函数 | **这个 Actor 在客户端也存在** |
| **`UPROPERTY(Replicated)`** | 属性 | **这个属性要同步** |
| **`GetLifetimeReplicatedProps`** | 类 | **列出哪些属性参与复制** |

**三者缺一不可。只加 `Replicated` 不写 `GetLifetimeReplicatedProps`，属性不会复制。**

## 二、核心类（实测规模）

| 类 | 头文件 | 大小 | 职责 |
| --- | --- | --- | --- |
| **`UNetDriver`** | `NetDriver.h` | **112,293 B** | **网络驱动**：连接、收发包、Actor 相关性 |
| **`UNetConnection`** | `NetConnection.h` | 80,000 B | 单个连接 |
| **`FRepLayout`** | `RepLayout.h` | **66,419 B** | **复制的内存布局**（哪些字节怎么序列化）|
| `FRepState` | 同上 | — | 单个对象的复制状态 |
| `FNetBitWriter` | `NetSerialization.h` | 22,314 B | 位级序列化 |

### 2.1 `UNetDriver` 的关键方法（源码确认存在）

```
ServerTravel              ← 服务端切图
TickDispatch              ← 收包
TickFlush                 ← 发包
ProcessRemoteFunction     ← 处理 RPC
ReplicateActors           ← 每秒若干次的复制主循环
```

**`ReplicateActors` 是核心 —— **它不是每帧跑，是有频率的**。
这解释了为什么复制的属性会有"延迟感"。**

### 2.2 `FRepLayout` 的关键方法（源码确认存在）

```
SerializeProperties       ← 序列化（读写都用这个）
SendProperties            ← 发送
ReceiveProperties         ← 接收
BuildSharedSerialization  ← 编译期构建共享布局
```

**`FRepLayout` 是**编译期**生成的 —— 它把类的属性布局"烘"成一份描述，
运行时按它逐字段序列化。**这就是为什么改属性后要重新编译。**

## 三、四种 RPC 与三种属性标记

### 3.1 RPC（远程调用）

| 标记 | 方向 | 用途 |
| --- | --- | --- |
| **`Server`** | 客户端 → 服务端 | **请求**（我要攻击）|
| **`Client`** | 服务端 → 拥有者客户端 | **通知**（你被击中了）|
| **`NetMulticast`** | 服务端 → 所有客户端 | **广播**（有人放了技能）|

**修饰符：**

| 修饰 | 含义 |
| --- | --- |
| `Reliable` | **保证到达**（重要事件）|
| `Unreliable` | 可能丢（位置更新）|
| `WithValidation` | **带校验函数**（防作弊，服务端验证参数）|

### 3.2 属性标记

| 标记 | 用途 |
| --- | --- |
| **`Replicated`** | 服务端改，客户端收 |
| **`ReplicatedUsing=OnRep_X`** | 收到后**调回调**（可以做特效、动画）|

**`ReplicatedUsing` 是"数据到了要做事"的机制 ——
比如血量变了要飘伤害数字，就是它。**

## 四、引擎自身的使用统计（实测）

**扫了 6,001 个头文件，统计各标记出现次数：**

| 标记 | 次数 |
| --- | --- |
| `Server` | 20 |
| `Client` | 18 |
| `Replicated` | 8 |
| `RepNotify` | 5 |
| `ReplicatedUsing` | 0 |
| `NetMulticast` | 0 |

**⚠️ 这个统计口径有问题** —— 引擎源码里复制的实际用量远大于此
（`PlayerController.h` 一个文件就有多处）。**原因是我的正则只扫了前 6000 个文件，
而且只统计 `UPROPERTY`/`UFUNCTION` 上下文里的精确词。**

**所以这个数字**不能当结论用**，只能说明"我扫的这个范围里有多少"。
这个诚实标注本身比数字重要。**

## 五、🔴 关键区别：UE 的复制 ≠ 墨香的服务端

**这两件事完全不相干，必须分清：**

| | UE 的复制机制 | 墨香的服务端源码 |
| --- | --- | --- |
| 是什么 | **引擎内置的同步框架** | **一个具体的游戏协议实现** |
| 用途 | 做**我们自己的**联机游戏 | **理解原作怎么跑** |
| 协议 | UE 自己的 | 墨香自己的（自研） |
| 能对接吗 | ❌ **不能** —— 协议完全不同 |

**所以：**
> **即使将来架起墨香服务端，也不会走 UE 的复制 —— 那是两个独立的系统。**
> **墨香服务端的研究价值在"理解设计"，不在"和 UE 对接"。**

**这条认知很重要 —— 它防止把两个不同层面的东西混为一谈。**
