# UE5 UI：UMG / Slate / Canvas 三层，与 Python 的边界（实测）

> **结论先行：从 Python 建 UMG 布局**做不到** —— 不是"难"，是**没有路径**。
> 类型都在，但资产到控件树的连接没暴露。**
>
> **证据是本篇的全部内容。**

---

## 一、三层结构

```
Slate（C++，底层）
  SWidget / SWindow / SlateStyle
     ↑ 被包裹
UMG（蓝图可做，上层）
  UWidgetBlueprint / UWidgetTree / UPanelWidget
     ↑ 运行时
游戏 HUD
  本项目用的是 ALXJHUD（Canvas 直接画）
```

| | Slate | UMG | Canvas HUD |
| --- | --- | --- | --- |
| 语言 | C++ | 蓝图 + C++ | **C++ 直接画** |
| 能做交互控件 | ✅ | ✅ | ❌ 只能画 |
| 做起来快吗 | 慢 | 中 | **快** |
| 适合 | 编辑器 UI | **游戏 UI** | 血量/准星这类简单显示 |

---

## 二、🔴 实测：Python 能做到哪一步

### 2.1 能做的：创建 Widget Blueprint 资产

```
UMG: created, class=WidgetBlueprint
```

**`unreal.WidgetBlueprintFactory()` 可用，资产能建出来。**

### 2.2 做不到的：往里面加控件

**逐项验证结果：**

| 检查 | 结果 |
| --- | --- |
| **`WidgetBlueprint` 的 widget/tree/root 属性** | **一个都没有**（`dir()` 里零匹配）|
| `WidgetBlueprint` 类级别 widget 名字 | **零** |
| **`WidgetBlueprintLibrary`** | **不存在** |
| `UMGBlueprintLibrary` | 不存在 |
| **`UMGEditorSubsystem`** | **未暴露** |
| **`WidgetBlueprintEditorSubsystem`** | **未暴露** |
| `WidgetTree` 类型 | ✅ 暴露 |
| `PanelWidget` 类型 | ✅ 暴露 |
| `TextBlock` 类型 | ✅ 暴露 |
| `CanvasPanel` 类型 | ✅ 暴露 |

**这是关键的不对称：**

> **控件**类型**都暴露了（可以 `new_object(TextBlock)`），
> 但**没有任何属性**把 WidgetTree 挂到 WidgetBlueprint 上。**
>
> **能造零件，造不出结构。**

### 2.3 这意味着什么

| 想做的事 | Python 能做吗 |
| --- | --- |
| 建一个空的 Widget Blueprint 资产 | ✅ 能 |
| 往里面放一个 TextBlock | ❌ **不能** |
| 读一个已有 Widget Blueprint 的控件树 | ❌ **不能** |
| 改控件的属性 | ❌ 拿不到控件 |

**所以 UMG 布局**必须手点编辑器**，或者写 C++。**

## 三、这对本项目的实际影响

### 3.1 项目需要什么样的 UI

**AGENTS.md 的硬性美术要求：**
> **UI/HUD：毛笔感字体、暗底 + 细金边、竖排或仿篆刻标题；不要现代扁平卡片式按钮。**

**这需要：**
- 自定义字体（毛笔感）
- 自定义样式（暗底金边）
- 自定义控件（竖排文字）

**Canvas HUD 画不出来这些** —— 它只能画矩形和文字，没有样式概念。

**所以必须用 UMG。**

### 3.2 三条可选路径

| 路径 | 做法 | 代价 |
| --- | --- | --- |
| **A. 手点编辑器做 UMG** | 人在编辑器里拖控件 | **一次性工作，但必须人做** |
| **B. 写 C++ 建控件** | `C++` 里 `CreateWidget` + 遍历控件树 | 中，但能自动化 |
| **C. 继续用 Canvas HUD** | 只用矩形+文字 | 便宜，**但达不到美术要求** |

**我的建议：A 为主，B 作为将来要做批量 UI 时的升级。**

**理由：** UI 布局是**设计决策**，不是批量机械劳动。253 个窗口脚本已经分析过，
**布局参数是有的，但"好不好看"需要人看**。

**所以这一块**不该追求自动化**，这和材质/网格不一样。**

### 3.3 本项目 UI 现状

| 项 | 状态 |
| --- | --- |
| `ALXJHUD`（Canvas） | ✅ 有，画血/灵/技能栏 |
| UMG 框架 | ❌ **没有** |
| 自定义字体 | ❌ 没有 |
| 样式表（SlateStyle） | ❌ 没有 |
| Widget 蓝图 | ❌ 没有（测试用的 `WBP_Test` 是空的）|

## 四、Slate 与 SlateInspector 的区别（容易混）

| | Slate | `SlateInspectorToolset` |
| --- | --- | --- |
| 是什么 | **游戏/编辑器的 UI 框架** | **驱动编辑器 UI 的自动化工具** |
| 用在哪 | 做界面 | 点按钮、读面板 |
| 对本项目 | 做游戏 UI 要用 | 自动化编辑器时用 |

**`SlateInspectorToolset` 是 22 个工具集里唯一和 UI 有关的，但它**不是**做 UI 的。**

**它对我们真正的用途：**
- 替代 `EditorGuard` 里硬编码坐标点模态框
- 按控件名点击，不怕窗口位移

**这条记在这里，将来模态框再捣乱就用它。**

## 六、下一步（诚实建议）

**UI 不该由我自动化。理由：**

1. **布局是设计决策**，不是批量劳动
2. **好看与否需要人眼判断**
3. **Python 这条路被官方关掉了**（不是我没找到）

**该做的是：**

```
1. 人（或我配合）在编辑器里做 1-2 个 UMG 控件
2. 确认样式（毛笔字体 + 暗底金边）能达到美术要求
3. 再决定要不要写 C++ 做批量
```

**在此之前，UI 这块的知识停留在"知道边界"，是**合理的**，不是偷懒。**
