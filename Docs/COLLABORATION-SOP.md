# 协作 SOP（逆向研究与资料归档）

> 这套循环在《墨香》客户端逆向中跑了几十轮，**每轮都有可验证产出**。
> 不只适用于逆向——任何"信息量大、边界不清、需要长期推进"的任务都能套。

## 一、每轮的标准循环（六步）

```
① 定范围   一句话说清这轮挖什么、预期产出什么
② 做一块   只做一件事，不并列三件事
③ 验证     脚本/日志/提交号，没有证据不算做完
④ 归档     立刻 commit，不攒着
⑤ 记教训   失败与新坑写进 pitfalls，含"症状→原因→正确做法"
⑥ 报结果   结论先讲，含负面结果
```

**关键约束**：一轮只做一个块。同时改三样东西必然有一半无法归因。

## 二、遇到"解不出来"时的自检顺序

按顺序排查，**先便宜的后昂贵的**：

| 顺序 | 检查 | 本项目实例 |
| --- | --- | --- |
| 1 | **目录对吗？** | 196 张表在 `slot0_plain/` 而非 `bin_plain/` |
| 2 | **解密方案对吗？** | TitanMixList 是 slot-0 哨兵加密，不是普通槽 |
| 3 | **文件名对吗？** | `.bin_out` 应为 `.bin.out`，静默输出 0 行 |
| 4 | **编码对吗？** | 158 张表是 EUC-KR，不是 GBK |
| 5 | **偏移对吗？** | 副本 id 200 对应任务组 1（差 199） |
| 6 | **字典键重复吗？** | `MonsterList` 定义两次，后者覆盖前者 |

**这六条覆盖了本项目 80% 的"卡住"**。

## 三、四个可复用的数据技巧

### 1. 名字关联（可读性分水岭）
任何"有 id 没名字"的表，先做一次名字关联再给人看。
`@HUNT 1` → `@HUNT 小呆呆`，一行脚本立刻变成可读设计。

### 2. 固定偏移
两表"看起来 id 不对应"时，先测固定差值（±1、±100、±199）。
往往不是没关系，是**编号基准不同**。

### 3. 自举词典
两张表有共同键时，用共同键**自动学出翻译表**，不要手工对应。
本项目用它从 `MapChange` 学出 81 条韩中地名对照，后续复用 6 次。

### 4. 受控对照（最强证据）
**同一实体的两个变体**是最可靠的证据源。
`桃木` vs `桃木+1` 一比对，强化等级列立刻暴露（100% 恒 +1）。
**比任何相关系数都可靠。**

## 四、统计结论的三条铁律

1. **相关性别当因果** —— 我在这上面错了两次（物品列 21 得 r=0.73，其实是"0 对 0"的假象）。
2. **必须看极值样本** —— 平均值会骗人，最贵/最便宜的样本最能说明问题。
3. **区间/上限不能当基础值** —— 稀有词条区间是"能 roll 到多少"，不是"物品有多少"。

## 五、归档纪律

| 什么 | 放哪 | 频率 |
| --- | --- | --- |
| 工具脚本 | `Tools/`，提交进 git | 每个新分析一个 |
| 派生数据 | `tables/*.csv`，**不进 git**（版权） | 每个解析一个 |
| 技术文档 | `Docs/*.md` | 每个系统一篇 |
| 教训 | `Docs/pitfalls.md` | 每轮有新坑就加 |
| 成就 | `Docs/achievements.md` | 每轮有产出就加 |

**派生数据必须能由工具重新生成**——工具进 git，数据不进。

## 六、诚实原则（最重要）

1. **不确定就标注**：`monster_item_refs` 不是"掉落表"，因为证据不支持。
2. **负结果也归档**：交叉相关 r=0.34 不成立、物品列两次推断失败——写下来，避免重复投入。
3. **修正要明说**：我判定"战斗公式不可得"是错的，改成"框架在文本里，只差两个常数"。
4. **宁可交标注不确定的引用表，也不交一张假的成品表。**

## 七、判断"该收线了"的信号

- 连续两轮**没有新结构产出**，只是在已有表上换角度；
- 剩下的缺口已被**证据证明不在可达范围内**（如服务端规则）；
- 边际产出变成"字段名"而不是"新内容"。

**这时应该转向使用资料，而不是继续挖。**
